## Release Theme

Full-stack reliability hardening. 81 verified, individually-tested fixes
found via systematic audit (not ad-hoc patching), spanning frontend
data-fetch error handling, backend process-crash prevention, resource
leaks, and a likely fix for a previously-known, unresolved bug.

## Production Changes

**Dominant bug class (74 instances) — VERIFIED: silent failure shown as
"0, all healthy."** Dozens of overview pages, dashboard widgets, and
hooks aggregated failed data fetches identically to a genuinely empty/
healthy state, with no error indication. Fixed across Workloads/
Resources/Scaling/Admission/CRDs Overview, the Dashboard's health score
widget, Intelligence Panel, Security assets, Pod status distribution, 4
Dashboard widgets, 3 project dialogs, and `clusterPresenceStore`. Several
pages already had correct error-handling code that was silently dead
because the underlying hook never provided the `isError` signal.

**Backend process stability — VERIFIED: panic recovery on all 26
previously-unprotected goroutines.** Zero `recover()` existed anywhere in
the backend before this release; an unhandled panic in pod exec, shell
streaming, port-forward, Fleet aggregation, metrics collection, or
topology rebuild crashed the entire backend process for every connected
cluster. 3 real deadlock bugs found and fixed while implementing
(non-deferred channel closes that would have hung forever on a panic).

**Resource leaks — VERIFIED, 2 real P1s:**
- Goroutine + underlying K8s exec/attach connection leak on pod exec /
  shell / kcli terminal disconnect (any session with buffered output in
  flight at disconnect — not rare for a desktop app).
- HTTP connection leak on every retried/failed Artifact Hub registry
  request (confirmed anticipated path via existing 429 Retry-After
  handling, not hypothetical).

**Cluster-switch race condition — CODE-PROVEN, likely root cause of a
previously-known, unresolved bug.** `keepPreviousData` on the app's two
most-used data hooks showed the *previous cluster's* resource list —
unlabeled as stale, `isLoading: false` — for the duration of a new
cluster's fetch after switching. Scoped to only apply within the same
cluster.

**CI fixes (unrelated to the above, found while preparing this release):**
- `charts-publish.yml`: `cosign-installer@v4` never existed upstream,
  pinned to `@v3` (shipped independently to both `origin` and `upstream`
  before this release).
- `collector_k8s.go`: pre-existing `staticcheck SA1019` finding (a Go
  lint tool version bump in CI newly flagged intentional deprecated-API
  usage), suppressed with justification.
- `security-scan-full.yml`: discovered disabled by GitHub's automatic
  60-day-inactivity policy — the weekly Trivy/Kubescape/Gitleaks/Semgrep
  scan had been silently dead for 2+ months. Re-enabled.

**Security and concurrency — AUDITED, confirmed clean (not "didn't
look").** Two full adversarial passes: XSS, SQL injection, path
traversal, RBAC gap, secret-in-logs (zero exploitable findings — one
process-note on RBAC pattern consistency, not a vulnerability); data
races, unprotected shared state, WaitGroup misuse (zero confirmed races —
traced every candidate to deliberate, documented mutex discipline).

## Known Issues (Pre-Existing, Not Blocking)

- 3 frontend test failures (`ClusterPickerPage.test.tsx` x2,
  `AddClusterDialog.test.tsx` x1) — confirmed pre-existing via baseline
  worktree comparison, not a regression. Text-expectation/component-copy
  mismatches, not functional bugs.
- npm audit: 2 critical CVEs (tinypool / vitest, both dev/test-only
  dependencies, zero production exposure — confirmed via dependency-path
  analysis: neither appears in `dependencies`, only `devDependencies`;
  zero production source files import either package outside
  `src/test-setup.ts`). Safe fix requires vitest 2→4 **and** vite 5→6 (a
  production build-tool major bump), confirmed via direct, reverted
  attempt to break 107/108 test suites at the collection/configuration
  level — a systemic test-environment incompatibility, not a few failing
  assertions. **DEFERRED** as its own dedicated migration task (see
  "Frontend Test Infrastructure — Vitest 4 Migration" below), not safe to
  rush into a production release.
